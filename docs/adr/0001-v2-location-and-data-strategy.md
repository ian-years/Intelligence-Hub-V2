# ADR-0001: V2 目录位置与数据策略

- **状态**：Accepted
- **日期**：2026-09-22
- **决策人**：用户 + Qoder
- **相关**：Q1（代码起点）、Q2（目录与数据）

## 背景

V1（`E:/08-Codework/Intelligence-Hub`）已稳定运行，含 466+ 测试、四平台真机实测可达、大量「踩出来的契约」（V1 `AGENTS.md` §7 共 25 条）。

用户要求：
1. **保存当前工作区不要影响**（V1 一行不动）
2. **另起一个目录**做 V2 重构
3. V2 走标准工程化规范
4. V3 仍是全量重写，所以 V2 设计要为 V3 留好接口

## 选项

- **(A) 全新重写**：V2 从零起，只参考 V1 的契约与陷阱清单，不复制代码
- **(B) 重组+移植**：V2 起标准 Python 包骨架，把 V1 的采集器、桥客户端、ASR、local_store 作为**实现**移植到对应接口后面
- **(C) 同仓 monorepo**：V1 V2 共存一个仓，V2 在子目录

数据层独立选项：
- 完全独立（独立 `data/`，不读 V1 数据）
- 独立代码 + 共享数据（V2 代码独立，但数据目录指向 V1）
- 独立 + 一次性迁移（V2 独立目录，附迁移脚本）
- 独立 + UI 按需导入

## 决定

**代码起点：(B) 重组+移植。**

理由：
- 用户强调「不要影响 V1」，但 V1 §7 那些平台陷阱是真机踩出来的资产，重写一遍代价高且容易回退
- 工程化收益主要在边界（接口/调度/配置/UI），不在采集器内部算法
- 移植时按「接口先行、实现照搬、契约测试托底」做，V1 工作区一行不动

**目录位置**：`E:/08-Codework/Intelligence-Hub-V2/`（与 V1 同级，独立 `git init`，远程仓库可新建或先空着）。

**数据策略：独立 + 一次性迁移。**

- V2 独立目录、独立 git、独立 `data/`
- 附 `tools/migrate_from_v1.py`：从 V1 SQLite 复制博主 / 视频元数据 / 口播稿，**只读 V1**（`file:...?mode=ro` URI），不写 V1 任何文件
- 媒体文件可选策略 `--media-strategy {copy|hardlink|symlink|reference}`，默认 `hardlink`（同盘 instant、省磁盘），失败自动降级 `copy`
- 不迁移 `cdp-bridge-profile/`（让用户在 V2 重新登录一次，profile 与 Chrome 版本绑定）
- 不迁移 ASR 模型（233 MB，V2 配置里指向 V1 路径即可）
- 迁移幂等、可恢复（`data/.migration_state.json`）、支持 `--dry-run` 与 `--rollback`

## 后果

**好处**：
- V1 工作区零风险，V1 那些"形状烂但行为对"的代码作为参考实现保留
- V2 数据完全自主，schema 演化不被 V1 历史绑架
- 一次性迁移成本可控，博主库与历史口播稿（真金白银的资产）保住

**代价**：
- 移植过程要识别哪些是 V1 的"形状烂但行为对"代码（如抖音 `yt-dlp → 页面播放直链` 兜底），照搬逻辑、重塑结构
- 迁移脚本是一次性投入（约 500 行）
- V1 / V2 短期共存，文档要清楚标注哪份是哪份

**对 V3 的意义**：
- V3 启动时，V2 的接口契约（Protocol + Pydantic 模型 + JSON Schema）已经过 V2.0/V2.1/V2.2 三轮真机验证，是 V3 重写的可执行规范
- V3 仍走"独立目录 + 一次性迁移"模式（V2 → V3 迁移脚本与 V1 → V2 同构，可复用）

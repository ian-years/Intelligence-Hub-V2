### 做了什么

### 三条"在文件里看不出来的错"，每条都做了变异检查

这个端点的危险不在"报错"，在**静默给出错的数据**。所以三条规矩各配用例，并且我把实现改坏
去确认用例真的会红（`verification-before-completion` 意义上的证据，不是"我写了断言"）：

| 规矩 | 变异 | 结果 |
|---|---|---|
| 公式注入中和（`= + - @` 与前导空白变体），**只中和字符串** | 判据放宽到所有值 | `test_a_negative_number_is_not_quoted_away_as_text` 红 ✓ |
| 同上 | 完全不中和 | 恶意标题 5 格红 ✓ |
| **翻页翻到 `total` 对齐**（列表端 `size<=200` 不是导出的上限） | 只取第一页 | 250 行那条红 ✓ |
| CSV 带 UTF-8 BOM（中文 Windows 的 Excel 按 GBK 猜） | —— | 用例直接断前三个字节 |

"少翻一页"得到的是一份**看起来完整**的 CSV，行数对不对在文件里根本看不出来，
所以 250 行那条种子是这一格里最值钱的用例。负数那条同样重要：`-5` 加 `'` 前缀会变成文本，
Excel 整列求和就废了 —— 判据太紧与太松都会红，取值故意选 `-5`（既是合法负数又在起手字符表里）。

另外两处刻意的设计，都写在代码注释里：
列清单手写而不是从模型字段推（新增内部字段不该自动进别人的表格；`metadata_json` 一行几十 KB
的 V1 raw_data 明确不导）；文件名不含任何请求输入（它要进响应头，一个带 CRLF 的参数
就能 header injection，用例专门拿 `x"; filename="pwned` 去试）。

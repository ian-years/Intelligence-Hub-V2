### P0-1 【已核实】B站空间枚举恒抽不出一条作品：`-J` 与解析器的契约不匹配

```python
# src/intelligence_hub_v2/platforms/bilibili/listing.py:128-147
def parse_dump_json_lines(stdout: str) -> list[dict[str, Any]]:
    """`--dump-json` 是**一行一个 JSON**，不是数组。"""
```

**证据链**（三方互相矛盾）：

| 来源 | 说的命令 |
|---|---|
| `ytdlp.py:352` 实际构造 | `-J` |

### P0-2 【已核实】合并成功的下载被判成"没产出文件"

```python
# src/intelligence_hub_v2/infra/ytdlp.py:462-465
marker = "[download] Destination: "
if line.startswith(marker):
    ...
```

`_path_from_line` 只认 `[download] Destination:` 和 `has already been downloaded`。但合并后的文件由 `FFmpegMergerPP` 产出，打的是 **`Merging formats into "xxx"`**（`.venv/.../yt_dlp/postprocessor/ffmpeg.py:840`，已 grep 确认），且合并后原分片被删除。

于是 B站 `-f bv*+ba/b --merge-output-format mp4` 这条常规路径下，stdout 里的两个 `Destination:` 路径**都已被删** → `classify_artifacts` 全部 `kind="empty"` → `adapter.py:449` 抛 `MediaDownloadError("退出码 0 但没有产出可读的文件")`。**媒体已经好好躺在磁盘上，却判失败。**

**改法**：`_path_from_line` 增加 `Merging formats into "(?P<path>.+)"` 规则；或更稳——加 `-O after_move:filepath` 把最终落盘路径作为权威来源（yt-dlp 官方推荐的取产物方式）。二者都不违反"绝不扫目录"的纪律。

### P0-4 【已核实】`_build_context` 失败 → 留下永不终结的 `running` 行 + 零清单

```python
# src/intelligence_hub_v2/core/task_runner.py:94-105
await self._storage.task_runs.start(...)          # 94：先插 running 行
ctx = self._build_context(...)                    # 101：不在下面这个 try 里
try:
    await self._run_to_terminal(...)
finally:
    await self._discard_workdir(ctx.workdir)      # 只清目录，不补终态
```

`_build_context`（`:168-191`）里有三处会抛：`tmp_dir(create=True)` 的 `OSError`、`DepsFactory.default()` 的 `TaskRejected`、`_configs[platform]` 的 `KeyError`。

`manifest_writer` 的"五条退出路径必落终态"保证**只覆盖 `async with` 内部**。结果是：`task_runs` 里一条 `status='running'` 且 `ended_at IS NULL` 的行永久留存（只有进程重启的 `mark_orphans_failed` 才清）、**一条清单都没写**、不发任何 `task.failed` 事件 → 前端是永远转不出来的进度条 + 永远等不到收尾的 SSE。

**最恶劣的触发路径**：`preflight` 的 `platforms=()` 对空平台直接放行；当所有平台都被关掉（配置坏了）时，用户点的恰恰就是 `preflight` —— **"环境已经坏了、用来检查环境的那件事本身也坏了"**。

**改法**：把 `start()` 之后到 `manifest_writer` 之间的整段纳入终态保证，异常时补一次 `finish(status="failed", error_text=...)` 再 raise（`finish()` 自身也要包 try/except 只记日志）。

## 5. 核心洞察：看护的是「另一条路」

这个仓库最擅长的就是防"文档说有看护而实际没有"（`AGENTS.md §5` 明说踩过两次，`test_contract_guard_index.py` 就是为此造的）。但 4 个 P0 是同一种新形状：

| 问题 | 被验证的路径 | 实际跑的路径 |
|---|---|---|
| P0-1 `-J` | `FakeYtDlpRunner` 喂 `-j` 形状 fixture | 真子进程跑 `-J` |
| P0-2 合并 | 测试喂"单格式不合并"的 stdout | 真机走 `Merging formats into` |
| P1-2 SSE `since` | 用例传 `taskId:"t1"` | 生产 `useTaskEvents()` 无参 |
| P1-8 本地门禁 | CI 内联命令 | Makefile 目标从来跑不通 |

**"1301 passed"是真的，"25 条每条有归属"也是真的，但真机那一半的缺口没有被任何东西看护** —— 而 `ROADMAP.md` 里那两个未勾的里程碑恰恰卡在这里。

**一条可落地的补法**：给"命令 flag 与实际子进程行为"加一层**不需要网络**的看护——把 argv 构造与 stdout 解析器用同一份契约钉住（例如一条用例同时断言"构造出的 argv 含 `-j`"与"`parse_dump_json_lines` 吃 `-j` 的输出"，且两者指向同一个常量）。P0-1 就是这两件事各写各的才漂掉的。
